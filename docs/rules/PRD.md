# 매그파이 PoC — 7일 스프린트 PRD (최종)

> **문서 목적**: 매그파이(아침 10분 AI 회화 앱) 전체를 만드는 것이 아니라, **핵심 루프 하나만 완결도 있게 검증**하는 1주일짜리 PoC를 위한 기획 문서. 프론트엔드 캠프 플래그십 과제("AI 기능이 들어간 프로덕트 화면") 제출용이며, 이 문서를 AI 코딩 어시스턴트에게 하루 단위로 넘겨 작업을 진행한다.
>

## 0. 이 문서 사용법

- 매일 아침, 해당 Day 섹션 전체를 AI 코딩 어시스턴트에게 컨텍스트로 제공하고 그날의 "산출물" 기준으로 작업을 요청한다.
- Day가 끝나면 **Definition of Done**을 체크하고, 못 끝냈으면 "잘라낼 순서"(11장)를 참고해 스코프를 줄인다.
- 기술 스택은 5장에 확정 근거와 함께 명시했다. 다른 스택을 쓰고 싶다면 5장과 7장(어댑터 인터페이스명)만 교체하고 나머지는 그대로 쓴다.
- 7장(설계 원칙)은 이번 주뿐 아니라 이후 네이티브 앱 전환 때도 지켜야 할 원칙이므로 특히 신경 써서 읽는다.

## 1. 배경 & 문제 정의

매그파이는 "아침마다 10분, AI와 대화하며 회화 능력을 기르는 앱"이라는 아이디어다. 하지만 앱 전체(로그인, 결제, 학습 기록, 통계 등)를 1주일 안에 만드는 것은 불가능하고, 캠프 과제가 요구하는 것도 완결된 프로덕트가 아니라 **AI 기능이 들어간 화면 하나**다.

그래서 이번 PoC는 매그파이의 존재 이유인 **단 하나의 코어 루프**만 검증한다:

> **"정해진 시간에 알림이 온다 → 대화가 시작된다 → LLM과 스트리밍으로 자연스럽게 티키타카가 된다"**
> 

이 루프가 프론트엔드 관점에서 매끄럽게 동작하는지가 이번 프로젝트의 유일한 성공 기준이다.

## 2. 목표 / 비목표

### 목표 (Goals)

- 지정 시각에 브라우저 알림이 실제로 울린다.
- 알림 클릭 시 대화 화면으로 진입해 즉시 세션을 시작할 수 있다.
- 음성 또는 텍스트로 발화하면 Claude API 응답이 **토큰 단위 스트리밍**으로 렌더링된다.
- 로딩·에러·빈 화면·권한거부 등 모든 예외 상태가 UI로 명시적으로 처리된다.
- 접근성(스크린리더, 키보드 내비게이션, 음성 미지원 환경 폴백)이 확보된다.
- 성능 최적화 전/후를 Lighthouse·번들 크기 수치로 비교 제시한다.

### 비목표 (Non-goals) — 이번 스프린트에서 하지 않는 것

- 회원가입/로그인/사용자 계정
- 결제, 구독 로직
- 대화 히스토리 영구 저장, 학습 통계/대시보드
- 앱스토어 배포용 네이티브 앱 (웹앱으로 한정)
- 브라우저를 완전히 꺼도 오는 푸시 알림 (스트레치 목표로만 취급, 9장 참고)
- 다국어 학습 커리큘럼, 레벨 테스트 등 실제 "회화 학습" 콘텐츠 설계

## 4. 사용자 시나리오 (Happy Path)

> **핵심 변경**: 마이크 버튼을 눌러 발화하는 방식이 아니라, **핸즈프리 자동 턴테이킹**으로 진행한다. AI 질문 → 사용자 발화 → 무음 감지 → AI 응답 → 자동으로 다시 듣기, 이 사이클이 사용자 조작 없이 반복된다.
> 
1. 사용자가 설정 화면에서 알림 시간을 09:00으로 지정하고 알림 권한을 허용한다.
2. 09:00, 브라우저 알림이 뜬다 ("오늘의 회화, 준비되셨나요?").
3. 알림 클릭 → 대화 화면 진입, 인사말과 첫 질문이 스트리밍 텍스트 + TTS 음성으로 자동 출력된다 (사용자 조작 없음).
4. 질문이 끝나는 즉시 마이크가 **자동으로 활성화**되어 듣기 상태로 전환된다.
5. 사용자가 답변하면 실시간 인식 텍스트가 화면에 표시된다.
6. 사용자가 말을 멈추면(약 1.2초 무음 감지) 발화 종료로 판단, **자동으로 전송**된다.
7. LLM 응답이 토큰 단위로 스트리밍 렌더링되며 동시에 TTS로 재생된다. 이 동안 마이크는 자동으로 mute(에코 방지)된다.
8. TTS 재생이 끝나면 자동으로 다시 듣기 상태로 전환되어 사이클이 반복된다.
9. 3~5턴을 주고받은 뒤 사용자가 수동 종료 버튼으로 세션을 마친다.

### 예외 시나리오 (반드시 UI로 커버)

- 알림 권한 거부/미지원 브라우저 → 대체 안내 문구 + 수동 "지금 시작하기" 버튼 제공
- **무음 감지 오탐(false cutoff)**: 사용자가 생각 중인데 끊겼다고 오판 → "이어서 말하기" 버튼으로 즉시 수동 복구 가능하게 안전장치 제공
- 마이크 권한 거부/미지원, 또는 연속 음성인식 미지원 브라우저(Safari 등) → 텍스트 입력 모드로 완전 폴백. 텍스트 모드는 "전송" 버튼/Enter가 곧 턴 종료 신호이므로 무음 감지 로직이 필요 없어 오히려 단순함
- TTS 재생 중 마이크가 자기 음성을 인식하는 에코 유입 → 재생 중엔 인식기 자동 일시정지, 재생 종료 시 재개
- 네트워크 끊김/API 오류 → 재시도 버튼, 에러 메시지
- 스트리밍 중 사용자가 응답 취소 → 스트림 중단 처리
- 첫 진입 시 대화 없음(빈 화면) → 온보딩성 안내 문구

## 5. 기술 스택

> Next.js 대신 Vite(SPA)로 확정한 이유: 이 앱은 SEO/서버 렌더링이 필요한 화면이 없고(마이크·알림 권한을 전제로 하는 화면뿐), Web Speech API 등 브라우저 전용 API를 `'use client'` 경계 없이 바로 쓸 수 있다. Claude 프록시를 API Route로 합칠 수 있다는 Next.js의 이점보다, 프레임워크 오버헤드를 피하는 쪽이 1주일 타임라인에 더 유리하다고 판단했다.
> 
- **프레임워크**: React + Vite + TypeScript
- **상태관리**: 대화 화면은 `useReducer` 기반 상태머신 (아래 6장 참고), 전역 설정은 Zustand 또는 Context
- **스타일**: Tailwind CSS
- **LLM 연동**: Anthropic Messages API, `stream: true` (SSE)
- **API 키 보호**: Vercel Serverless Function으로 프록시 (Node.js 런타임이라 익숙한 문법 그대로 사용 가능; 프론트에서 API 키 직접 노출 금지)
- **음성 인식(STT)**: Web Speech API (`webkitSpeechRecognition`), feature-detect 후 미지원 시 텍스트 모드로 자동 폴백
- **음성 출력(TTS)**: Web Speech API (`SpeechSynthesis`)
- **알림**: Notification API + Service Worker (클라이언트 타이머 기반, MVP 범위), 서비스워커 등록·매니페스트 관리는 `vite-plugin-pwa`로 단순화
- **번들 분석**: `rollup-plugin-visualizer` — 빌드 후 모듈별 크기를 트리맵으로 확인 (6장 성능 작업에 사용)
- **모델 선택 전략**: 개발/테스트 중에는 `claude-haiku-4-5` (저비용), 최종 데모·리포트 캡처는 `claude-sonnet-5`로 전환

> **참고**: Web Speech API·SpeechSynthesis는 브라우저 내장 API라 번들 크기에 영향을 주지 않는다. 이 앱의 실질적인 번들 최적화 대상은 음성 API가 아니라 `ConversationScreen` 컴포넌트 트리 자체다 (10장 Day 6 참고).

## 6. 화면 & 컴포넌트 구조

### 화면 흐름

```
[알림 설정 화면] → (지정 시각 도달) → [브라우저 알림] → [대화 화면]
```

### 대화 화면 상태머신 (자동 턴테이킹)

```
assistant_speaking (질문/응답 TTS 재생 중, 마이크 mute)
  └─(TTS 종료)→ listening (마이크 자동 on)

listening → user_speaking (interim 인식 결과 수신 중)
user_speaking → (무음 ~1.2초 감지 또는 텍스트 전송) → sending
sending → streaming(LLM 응답 수신 중) → assistant_speaking → listening (반복)

안전장치: user_speaking/sending 상태에서 "이어서 말하기" 버튼 클릭 시 → listening으로 강제 복귀 (오탐 복구)
텍스트 입력 시: 무음 감지 불필요, "전송" 클릭이 곧 sending 트리거
어느 상태에서든 실패 시 → error → (재시도) → listening
```

`useReducer`로 구현해 "streaming 중인데 동시에 listening" 같은 불가능한 상태 조합을 원천 차단한다. 이 설계 근거는 컴포넌트 문서에 반드시 기록한다. 특히 이번엔 상태 전환이 **자동으로(사용자 클릭 없이) 발생**하므로, 각 상태 진입 시 `aria-live` 영역으로 "듣는 중 / AI가 답하는 중 / 생각 중" 등을 스크린리더에도 알려야 한다 (버튼 클릭이라는 명시적 상호작용이 사라진 만큼 접근성 신호를 더 명확히 보강).

### 컴포넌트 목록

- `NotificationSetup` — 시간 설정, 권한 요청, 권한 상태별 안내
- `ConversationScreen` — 상태머신 컨테이너
    - `ChatMessageList` / `ChatBubble` — user/assistant variant로 재사용
    - `TurnIndicator` — 현재 상태(듣는 중/생각 중/말하는 중)를 시각적+`aria-live`로 표시, 자동 전환의 핵심 UX 요소
    - `ResumeSpeakingButton` — 무음 오탐 시 "이어서 말하기" 안전장치 ("오탐 복구 + 일시정지" 용 컴포넌트)
    - `TextInputFallback` — 음성 미지원 환경에서 자동 노출, 전송 버튼이 턴 종료 신호
    - `StreamingIndicator` — 스트리밍 중 표시
    - `ErrorBanner`, `EmptyState`

## 7. 설계 원칙: 플랫폼 어댑터 분리 (중요)

이번 기능은 추후 네이티브 앱 전환(Web Speech API, Notification API 교체)을 염두에 두고 두 층으로 나눠서 만든다.

| 층 | 내용 | 이식성 |
| --- | --- | --- |
| **로직 레이어** (재사용 대상) | 대화 상태머신, 무음 감지 후 턴 전환 규칙, LLM 프롬프트/스트리밍 파싱 로직, "오탐 시 수동 복구 버튼을 둔다"는 UX 판단 | 플랫폼이 바뀌어도 그대로 유지 |
| **어댑터 레이어** (교체 대상) | Web Speech API(STT) 호출부, `SpeechSynthesis`(TTS) 호출부, `Notification`/Service Worker 호출부 | 네이티브 전환 시 교체 |

이를 위해 각 브라우저 API를 인터페이스 뒤에 캡슐화한다:

```tsx
interface SpeechInputEngine {
  start(onInterimResult: (text: string) => void, onSpeechEnd: () => void): void;
  stop(): void;
}
interface SpeechOutputEngine {
  speak(text: string, onEnd: () => void): void;
}
interface ReminderEngine {
  schedule(time: Date, onFire: () => void): void;
}
// 이번 주: WebSpeechInputEngine, WebSpeechSynthesisEngine, BrowserNotificationEngine
// 네이티브 전환 시: RNVoiceInputEngine, RNTTSEngine, ExpoNotificationEngine (상위 상태머신 무변경)
```

**마이그레이션 유의사항 메모** (지금 처리하지 않아도 되지만 기록해둠):

- **알림은 네이티브 전환 시 오히려 유리해진다** — `expo-notifications`로 앱 종료 후에도 진짜 예약 알림이 가능해서, 웹의 "포그라운드에 있어야 알림이 뜬다"는 제약(8장 MVP 범위)이 사라진다.
- **LLM 스트리밍 응답 처리에 의외의 함정이 있다**: 웹의 `fetch` + `ReadableStream` 조합을 React Native의 기본 `fetch`는 동일하게 지원하지 않는다. 네이티브 전환 시 별도 스트리밍 라이브러리(`react-native-sse` 등)나 웹소켓 방식으로 교체가 필요함을 미리 인지해둔다.
- UI 레이어(React DOM/Tailwind)는 네이티브 전환 시 React Native 컴포넌트(`View`/`Text` 등)로 다시 작성해야 한다 — 어댑터 분리로도 피할 수 없는 부분이며, 이번 주 설계의 이관 대상은 어디까지나 로직/파이프라인/판단 근거에 한정됨을 전제한다.

## 8. 비용 & 예산 가이드

- Claude API는 Claude.ai 구독과 **별개의 종량제 결제**이므로 platform.claude.com에서 별도 API 키/크레딧이 필요하다.
- 개발+데모 전체 기간 예상 비용: Haiku 4.5 기준 약 1,000~2,000원, Sonnet 5 기준 약 2,000~4,000원 수준 (턴당 짧은 대화 500턴 기준).
- 비용 통제 원칙:
    1. 대화 히스토리를 매턴 전체 재전송하지 않고 최근 N턴만 윈도잉
    2. 시스템 프롬프트는 프롬프트 캐싱 적용 (반복 재사용되는 페르소나/규칙)
    3. `max_tokens`로 응답 길이 상한 설정
    4. 개발 중 반복 테스트는 Haiku로

## 9. 스코프 분리: MVP vs 스트레치

| 구분 | 항목 |
| --- | --- |
| **MVP (필수)** | 클라이언트 타이머 기반 브라우저 알림, 무음 타이머 방식의 자동 턴테이킹(음성)+텍스트 하이브리드 입력, TTS 재생 중 마이크 자동 mute, 오탐 복구용 "이어서 말하기" 버튼, LLM 스트리밍 응답, 전체 상태(로딩/에러/빈화면/권한) 처리, 접근성 기본기, Lighthouse/번들 리포트 |
| **스트레치 (시간 남으면)** | Push API + 서버리스 함수로 브라우저 종료 후에도 오는 실제 예약 알림, 오디오 레벨 기반 정교한 VAD, AI 발화 중 사용자가 끼어들면 즉시 중단하는 바지인(barge-in) 지원, 반응형 세부 튜닝 |

MVP와 스트레치를 나눈 이유 자체가 "트레이드오프를 이해하고 스코프를 조절한 근거"로 컴포넌트 문서/발표에 활용 가능하다.

- `NotificationSetup` 화면, Service Worker 등록, 클라이언트 타이머로 지정 시각 Notification 표시

### Day 3 — 음성 입력 & 자동 턴 감지

- **DoD**: 음성 인식 텍스트가 화면에 실시간 반영, 말을 멈추면 자동으로 전송됨, 오탐 시 버튼으로 복구 가능, 미지원 환경에서 텍스트 입력창 자동 노출 확인

### Day 4 — LLM 스트리밍

- `ReadableStream` 파싱, 토큰 단위 렌더링
- 로딩·에러·빈 화면 컴포넌트 완성

### Day 5 — TTS & 자동 사이클 완성

- 음성↔텍스트 전환 UX, 반응형 기본 대응
- **DoD**: 전체 Happy Path(1→9)가 사용자 클릭 없이 자동으로 3턴 이상 반복 완주

### Day 6 — 성능 & 접근성

- 라우트 단위 코드 스플리팅: `const ConversationScreen = React.lazy(() => import('./ConversationScreen'))`으로 `NotificationSetup` 진입 시 대화 화면 코드가 함께 로드되지 않도록 분리 (Web Speech API 자체는 번들 무게가 없으므로, 실질 최적화 대상은 컴포넌트 트리 지연 로딩)

## 11. 잘라낼 순서 (시간 부족 시)

일정이 밀리면 아래 순서로 스코프를 줄인다. 핵심 루프(알림→입력→스트리밍 응답)는 끝까지 유지한다.

1. **자동 턴테이킹 → 수동 마이크 버튼 방식으로 축소** — 무음 감지 로직이 예상보다 불안정하면, 사용자가 버튼을 눌러 발화 시작/종료를 직접 트리거하는 방식으로 되돌린다 (설계 의도는 문서로 설명)
2. TTS(음성 응답 읽어주기) 제거 — 텍스트로만 봐도 스트리밍 데모는 충분
3. 반응형 세부 튜닝 축소 — 데스크톱 기준만 완성도 있게
4. 알림을 클라이언트 타이머 → 데모 트리거 버튼으로 대체 (기획 의도만 설명)
